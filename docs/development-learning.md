## Q001：搜索之后返回，为什么又变成默认页面？这些机制属于前端还是后端？

记录日期：2026-10-25。

**用户原话**

> 我搜索了我投递的银行，然后选了农业银行点进去，返回后我希望看邮储银行，但是我返回发现我之前搜索的没了，又变成默认界面了
>
> 面试问答模块也有类似的问题，包括不同模块间的切换再返回也是默认。
>
> 你说的这些机制是后端还是前端机制？

**用户发现的问题与期望**

在实际浏览过程中发现上下文丢失，要求查看详情返回、跨模块切换返回时保留搜索结果及浏览位置。需要保存的视图状态包括搜索词、筛选条件、排序、页码和滚动位置；问答按分类分别记录。

**概念解释：主要属于前端**

| 机制 | 所在位置 | 能解决的问题及边界 |
| --- | --- | --- |
| URL 参数 | 前端路由及浏览器地址 | 表达搜索、筛选、排序和页码，让链接与历史记录携带明确状态；并不自动保存滚动位置 |
| Pinia | 前端内存 | 在组件卸载后保留共享状态；单独使用不能保证刷新后仍在 |
| sessionStorage | 浏览器存储 | 在同一标签页会话内保留可序列化的状态，刷新后仍可读取 |
| localStorage | 浏览器存储 | 适合需要跨会话保留的偏好；需要自行处理版本、清理和失效 |
| KeepAlive | Vue 前端组件缓存 | 在应用运行时保留组件实例，减少重建；刷新会丢失，重新激活时仍要考虑数据更新 |
| 滚动恢复 | 前端页面或滚动容器 | 离开时记录位置，列表与布局就绪后还原；需找到实际滚动容器 |

投递记录和题目内容是业务数据，由现有后端与数据库负责；本条讨论的是用户当前如何浏览这些数据。当前同一浏览器中的恢复需求不要求新增后端接口。如果以后要实现同账号跨设备恢复，再考虑将必要的偏好同步到后端。

**实现前的问题定位**

- [投递列表](../frontend/src/modules/jobs/views/ApplicationListView.vue)：`keyword`、筛选项、`page` 和排序保存在页面局部状态中。
- [问答列表](../frontend/src/modules/qa/views/QaListView.vue)与 [问答 store](../frontend/src/modules/qa/store.ts)：已有单个 `listPage` 的局部页码记忆，但搜索和筛选仍在组件中；分类变化会主动清空。尚未实现按分类隔离的完整浏览状态。
- [布局](../frontend/src/layouts/BasicLayout.vue)：当前主内容直接渲染 `router-view`，没有统一页面缓存层。

**最初讨论的方案**

建立统一前端状态层，以模块、页面和分类 ID 隔离记录；用 URL 表达可分享的查询条件，用 Pinia 与 sessionStorage 恢复页面上次状态，并单独恢复滚动位置。KeepAlive 按需使用。业务数据继续沿用既有加载与更新流程，数据增删后校正超出范围的页码，非法参数按字段规则处理。

**实现与验证进展（2026-10-25）**

用户随后授权开始开发，AI 辅助完成三类列表的统一恢复层：URL 保存显式查询条件，Pinia 与 sessionStorage 管理各列表记忆，在实际滚动区域渲染就绪后恢复位置。当前未引入 KeepAlive；列表业务数据继续沿用既有 API 与 store。新增重置入口，问答分类切换清理批量选择，手撕题保持原列表返回路径。

为解决“刚输入就进详情”的情况，进入详情前先完成列表地址更新。为避免刷新时把第 3 页错误改成第 1 页，页码校正等待数据就绪后执行。上述细节由 AI 在实现与验证中补充，不记为用户最初提出的具体实现。

## Q003：登录缓存能维持多久，如何避免每次重新扫码？

回填日期：2026-10-25。

**用户原话**

> 这个小红书的登录缓存能维持吗，能维持多久，你知道的，我不希望每次使用都需要重新登录

**概念解释与边界**

本地持久化能保留凭据，平台服务端决定会话是否继续有效。应用关闭后凭据仍在，不代表服务端永久认可。本项目没有按固定天数清除登录的机制，也不能承诺平台登录能维持具体几天。搜索引用的 30 分钟有效期是另一项机制，不能视为登录有效期。

此处登录凭据由后端在本机保存，前端负责触发检查和显示状态；与 Q001 的浏览器页面状态保持分属不同职责。

**实现与验证依据**

已实现两种采集器分别保存登录；打开连接弹窗自动检查；CLI 有效响应后保存服务端轮换的 Cookie。访客响应和临时网络异常不覆盖旧缓存。见 [登录持久化说明](content-sources.md)、[CLI 工作进程](../backend/app/modules/experiences/sources/cli_worker.py)、[登录缓存验证](validation-content-sources-2026-10-25.md)。已有登录复用经过真实页面检查，但没有持续多日的有效期实验。具体修复由 AI 辅助完成。

**实现与验证依据**

## Q006：GitHub 为什么有两个分支，合并后完整的 commit 记录还在吗？

记录日期：2026-10-25。

**用户原话（摘录）**

> github为啥有了俩分支？这俩分支要是合并了完整的commit记录还在吗，还是只有main的记录了

**提问背景与解释**

当时仓库包含 `main` 和开发分支 `codex/fix-baseline-bugs-and-ui`；AI 将当前开发分支推送到 GitHub，推送前没有充分说明分支位置。用户据此追问开发历史是否会在合并时丢失。

| 方式 | 合并后的历史 |
| --- | --- |
| 普通合并 / Create a merge commit | 两边原提交保留，并通过合并提交连到 main；之后删除开发分支引用，也不删除 main 已能追溯到的提交 |
| Squash and merge | main 收到一个合并后的新提交，不逐条保留原开发提交；保留的原分支仍可单独追溯 |
| Rebase and merge | 逐个重放改动，通常产生新的提交编号，历史更线性；不等同于完整保留原提交身份 |

如果目标是保留原始开发过程，普通合并符合这个目标。2026-10-25 仅解释并继续在现有开发分支提交，当时尚未执行合并。

**用户决策与实际执行（2026-10-26）**

> 那你采用普通合并吧

按用户选择，由 AI 执行 `git merge --no-ff`，将 `codex/fix-baseline-bugs-and-ui` 合并到 `main`，合并提交为 [978877a](https://github.com/zizhseu/personal-app/commit/978877ab68e4574d00bc89ad02b578fba6a3b98b)。没有压缩或重放原提交，开发分支继续保留。

- 合并前确认工作区干净，两条本地分支均与 GitHub 对应分支同步。
- 合并没有冲突，两个父提交分别是原 `main` 的 `fb4ded1` 与开发分支的 `95d28ba`。
- 核对开发分支此次新增的 8 个原提交都可从 `main` 追溯，原提交编号保持不变。
- 合并提交的文件树与开发分支完全一致；这一步通过树差异与提交可达性验证，没有把此前的测试表述为本轮重新执行。
- 本次另补本条学习记录；数据库、参考仓库和本机凭据继续排除在提交外。

## Q008：同一公司换了岗位，为什么各阶段需要保存不同岗位？

记录日期：2026-10-26。

**用户原话**

> 某个公司的岗位我投递后挂了，于是我换了一个岗位，因此在流程中，不同的阶段应该显示不同的岗位，以此让使用者完整地回顾流程。

**用户发现的问题与产品要求**

用户从实际求职过程提出：一家公司的一条记录可能先投岗位 A、失败后再投 B，历史流程不能全部显示当前岗位。要求保留各阶段当时的岗位，便于完整回顾。

**定位与技术解释**

原模型只有 `application.position`，轮次与状态历史没有岗位快照；日程使用当前岗位拼接标题，当前结果也直接取全记录的最新轮次。仅修改前端文字或缓存不能保存过去的业务事实。

本功能与 Q001 的页面记忆不同，需要后端持久化岗位快照。岗位流程使用独立代次，A → B → A 仍是三次流程；结果保存所属阶段标识，补记旧轮次时不会被放到新岗位的同名阶段。

**AI 补充的实现细节**

- 更换岗位可选择重新初筛或继续当前阶段；普通编辑更改岗位也保存历史。同名再次投递可重新开始流程。
- 当前结果、截止时间和正向状态联动限定在当前岗位流程；旧岗位结果与复盘继续保留，上一岗位的 Offer 决定不沿用。
- 历史阶段可补录岗位并同步明确关联的快照；单独更正轮次岗位时处理冲突关联，不强行归到另一岗位。旧结果无法归属时仍显示。
- 原版本已经覆盖的岗位无法从现有数据可靠恢复。迁移保留未知，提供人工补录，而不是把当前岗位补成所有历史岗位。

这些方案与边界由 AI 在实现中补充，不能表述为用户亲自设计或独立编写。

AI 辅助修改后端模型、幂等迁移、岗位流程逻辑和前端展示；用户负责提出真实场景与回顾要求。完整后端 113 项测试、前端 20 项测试及生产构建通过；独立示例库完成改投、旧复盘、刷新、补录及窄屏验证。正式数据库先做本机备份，迁移后原记录和原字段逐项比对一致。没有声称自动还原未知历史，也没有把 AI 执行的检查写成用户亲自完成。

## Q011：电脑上运行的项目怎样通过局域网在手机访问？

记录日期为 2026-11-07（北京时间）。

**用户原话**

> 如何让局域网访问这个，比如现在是在电脑，我想在我的手机上也能访问

**用户需求与 AI 解释**

用户希望手机可以访问电脑上运行的项目。AI 核对现有启动脚本、Vite 配置和请求封装后，给出局域网访问的启动方式。

`127.0.0.1` 表示访问设备自身的回环地址。手机需要通过电脑的局域网 IPv4 地址连接电脑，前端服务也需要监听局域网接口。Vite 的 `--host 0.0.0.0` 用于监听本机所有 IPv4 接口，浏览器访问时填写电脑实际的局域网地址。

本项目的浏览器请求统一使用相对路径 `/api`，由电脑上的 Vite 代理转发到 `http://127.0.0.1:8000`。手机通过前端入口即可读取和编辑电脑数据库中的记录，后端沿用现有启动方式。

**给出的操作步骤**

手机和电脑接入同一路由器的网络，停止原前端进程后，在项目的 `frontend` 目录启动局域网入口。

```powershell
npm.cmd run dev -- --host 0.0.0.0 --port 5175 --strictPort
```

手机浏览器访问 `http://<电脑局域网IPv4>:5175/`。若出现 Windows 防火墙提示，可为 Node.js 允许专用网络访问。固定端口及 `--strictPort` 由 AI 补充，用于避免端口被占用后自动换号造成访问地址混淆。

AI 补充说明，现有投递接口允许直接读取和修改记录，局域网入口开放后，可连接该入口的设备也能操作这些数据。上述命令用于用户主动启动局域网访问。

**实际核对与阶段**

已检查 [启动脚本](../scripts/start.bat)、[Vite 配置](../frontend/vite.config.ts)及 [请求封装](../frontend/src/shared/api/request.ts)，并核对当前电脑的无线网络地址。本轮提供操作说明并记录原理，手机实机访问待验证。本条记录保留用户的使用需求及 AI 的方案解释，掌握程度留待用户个人复述或操作记录补充。
