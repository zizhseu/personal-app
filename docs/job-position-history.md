# 岗位变更与阶段历史

## 使用

同一家公司的一条求职记录可以经历多个岗位。详情顶部显示当前岗位，下方以岗位流程列表组织记录，每个岗位独立包含「流程轮次」和「状态变化」。主要岗位排在最前并默认展开，未明确选择时默认为最早的岗位；其他岗位可分别展开。「展开全部」便于对照，「仅展开当前」收起历史。

同名再次投递也分成不同流程，不会将 A → B → A 合并成同一组。旧版记录缺少岗位快照时，先按同次流程归属：若该流程只有一个已知名称，则空快照一同展示，不另造第二个岗位，也不修改数据库中的原始空值。只有整次流程名称均未知，或同代次存在多个名称且缺少明确关联时，才保留单独的未确认记录。结果变化按对应轮次归组，缺少可展示轮次的历史结果保留在所属岗位下。宽屏在组内并列显示轮次与状态，窄屏上下排列，主页面继续使用完整内容宽度。

例如：

| 阶段 | 岗位 | 结果 |
| --- | --- | --- |
| 原岗位初筛、笔试 | 岗位 A | 通过 |
| 原岗位面试 | 岗位 A | 未通过 |
| 更换岗位后初筛 | 岗位 B | 未开始 |

1. 进入投递详情，点击「更换岗位」，填写新岗位。
2. 默认勾选「重新从初筛开始」，保存后新增该岗位的初筛阶段及轮次，旧轮次、结果与复盘继续保留。相同名称再次投递，也可以开始新的独立流程。
3. 若新岗位继续当前阶段，取消该选项；例如仍处于面试阶段时，只新增新岗位的阶段记录，不借用旧岗位的面试结果。
4. 普通「编辑投递」更改岗位也会保留历史，表单可选择新岗位是否重新从初筛开始。仅修改备注或保存相同岗位，不会新增岗位流程。
5. 每个岗位下都可点击「添加轮次」，弹窗显示所选岗位。当前岗位沿用阶段与类型匹配规则，历史岗位可选择实际轮次类型补录。每个轮次下可展开「结果变化」，查看修改前后结果及时间。
6. 每组标题右侧可点击「删除岗位」。确认框显示岗位、岗位记录编号和待删记录数量；确认后清理该组的轮次、状态变化和结果。删除不可撤销，但不会按岗位名称批量删除同名的其他流程。
7. 投递列表的「主要岗位」列和详情信息卡的「主要岗位」都是下拉框，可直接选择任意现有岗位，选中即保存。岗位组上的「设为主要」也保留。默认最早的岗位只是初始选择，可随时切换，刷新后仍有效；同名不同流程在选项中用记录编号区分。列表显示所选岗位的名称、状态、结果及截止时间，看板采用同一口径。列表没有「最新轮次」列，也不展示轮次总数；详情仍展示各组的轮次与记录数量。
8. 每个岗位标题旁都可点击状态并选择初筛、复筛、面试或 Offer，保存后在该岗位下追加状态变化。列表状态入口修改所展示的主要岗位。各岗位均可直接操作，旧版「挂了」等状态也能重新选择。

删除历史岗位时，当前岗位保持不变。按用户确认的规则，删除当前岗位时保留公司和其他历史，当前岗位留空；删除最后一个岗位也保留公司记录。详情此时显示「暂无当前岗位」，可补录保留的历史岗位，也可点击「新增岗位」重新记录。公司备注、基本资料和独立日程保留。删除明确选中的主要岗位时，回退到最早的剩余岗位，若已无岗位则主要岗位也为空；其他删除不覆盖用户仍有效的选择。主要岗位的回退只影响列表展示，不将历史岗位恢复为当前岗位。没有主要岗位的公司不计入看板和状态筛选的岗位统计。

投递列表及看板的结果、投递列表的截止时间只使用主要岗位流程。日程保留有时间的测评、笔试、面试等实际安排（包括历史岗位的安排），展示轮次当时的岗位。日程主时间、排序与提醒颜色使用开始时间，已办事项也显示原定开始时间。只有截止时间的旧记录显示「开始时间待补充」，未完成轮次仍按截止时间判断过期，无截止时间时采用开始时间。初筛保存在流程详情。主要岗位选择负责列表展示，状态修改按具体岗位保存，公司资料继续通过投递编辑入口维护。各岗位的状态在组标题及列表中均可修改，Offer 决定沿用当前岗位的既有接口，轮次结果按真实轮次 ID 修改。通过「更换岗位」开始新流程时，仍按原规则清除当前 Offer 决定。

当前结果与详情使用同一归属规则。空快照若属于当前流程且只有唯一已知岗位名称，仍参与当前结果计算；若存在多名称冲突，则优先使用明确的阶段或轮次关联，仍无法确定时保留未知，不混入当前结果。

## 补录旧数据

旧版本只保存当前岗位，不能从数据库可靠还原曾被覆盖的岗位名称。升级时不把当前岗位填充成历史事实；同流程唯一名称的兼容归组仅是解释层，不能把「快照为空」本身当成「又投了一个岗位」的证据。旧阶段、轮次仍可主动补录事实。

- 在「编辑轮次 → 此轮岗位」补录或更正本轮的岗位快照，状态区域按所属岗位展示变化。
- 轮次岗位与原阶段记录冲突时，解除该轮次的冲突关联，结果变化按所属岗位和轮次展示。
- 缺少可展示轮次的旧结果保留在本岗位的「历史结果」中。
- 若当前岗位已在旧版本中被覆盖，可先补录旧轮次，再通过「更换岗位」为当前岗位重新开始独立流程。

## 保存规则

本功能属于后端业务历史持久化，与列表搜索、页码的前端会话记忆不同。

- `application.position` 为当前岗位，`position_version` 区分每次岗位流程。A → B → A 仍是三个不同的流程，不能仅靠名称判断归属。
- 内部代次不能直接用作页面的「第几次流程」：同代次更正成不同名称后可存在多个分组。页面使用独立的 `displayOrder`，按内部代次、该组最早记录时间、名称生成唯一的「岗位记录 N」；切换主要岗位不改变编号。此编号属于当前分组的展示序号，删除或更正分组后可能重新排列，不是永久业务 ID，也不用于推断投递次数。
- `primary_position` 与 `primary_position_version` 只保存用户的主要岗位选择，未选择时采用最早的岗位（按代次、最早记录时间和名称排序）；用户已保存的选择优先，不通过覆盖 `application.position` 实现切换。
- `status_history`、`interview_round`、`round_result_history` 保存岗位与流程代次快照。
- 轮次与结果保存 `status_history_id`，补记旧轮次的结果时优先归属旧阶段。结果历史在界面中按 `round_id` 展开到对应轮次下。
- 状态变化保存在对应岗位的 `status_history` 中。当前岗位同步 `application.status`，其他岗位取自己最新保留的状态记录。
- 正向推进状态沿用已有结果联动，只处理所选岗位的最新轮次。未开始、已完成或未参加的结果可转为通过，已记录的未通过结果保留。回退状态追加一条历史，轮次继续保留各自结果。
- 更换岗位支持 `expectedPositionVersion` 检查，陈旧表单返回 409；岗位流程递增使用数据库条件更新，避免同时改投时重复使用同一代次。

## 数据库升级与接口

后端启动自动补列，无新增业务表。新增字段为：

| 表 | 新增字段 |
| --- | --- |
| `application` | `position_version`、`primary_position`、`primary_position_version` |
| `status_history` | `position`、`position_version` |
| `interview_round` | `position`、`position_version`、`status_history_id` |
| `round_result_history` | `position`、`position_version`、`status_history_id` |

旧记录的代次初始为 1、岗位快照为空。一次性标记 `position_history_20261026` 只补有时间与状态依据的阶段关联，不猜测旧岗位名称；重复启动不覆盖人工补录。

`PUT /api/jobs/applications/{id}` 支持可选的 `restartProcess` 和 `expectedPositionVersion`，轮次更新支持可选 `{position}`，岗位长度上限为 100 字。早期客户端可通过 `PATCH /api/jobs/status-history/{id}/position` 维护历史快照。阶段删除后关联置空，岗位快照保留，删除整条投递时按既有级联关系清理历史。

`POST /api/jobs/applications/{id}/rounds` 可同时传入 `positionVersion` 和 `position`（未知岗位传 `null`），明确目标岗位流程；不指定时兼容原有当前岗位新增。服务端核对目标是否属于本条投递，历史阶段按所选岗位、流程和轮次类型匹配。可选 `expectedPositionVersion` 用于拒绝已变更岗位的陈旧表单；目标已被补录更名或删除时返回 409，客户端须刷新后重新选择。新增上下文字段不用于轮次编辑接口，也不新增数据库字段。

`DELETE /api/jobs/applications/{id}/positions` 的 JSON 请求体包含 `{position, positionVersion, expectedPositionVersion, expectedRoundIds, expectedStatusHistoryIds, expectedResultHistoryIds}`，未知岗位传 `null`。后三项记录用户确认的具体成员，数组可为空但不能省略或与当前归组不符；旧页面、过期卡片及范围变化均返回 409，不删除数据。删除范围沿用详情页一致的归属解释；若删除轮次会级联移除另一个岗位的结果，或存在跨公司阶段关联，也返回 409，要求先更正关联。

返回的投递记录包含计算字段 `hasCurrentPosition`，没有新增数据库列。删除当前岗位后保留一个无记录的新版本用于隔离陈旧请求，前端不将其显示为岗位；后续新增岗位使用更大的版本，不复用已删除流程的编号。空当前岗位不能通过旧的轮次或状态请求意外复活。编号用于区分流程，不能当作现有岗位总数。

`PUT /api/jobs/applications/{id}/primary-position` 保存 `{position, positionVersion, expectedPositionVersion}`。目标必须是当前记录中真实存在的分组，未知名称传 `null`；代次不匹配或目标被删除、更名时返回 409。接口只更新两列选择字段，连投递原 `updated_at` 也保持不变，不新增阶段或轮次。响应新增 `positionSummaries` 与 `primaryPosition`，包含展示序号、该组成员 ID、状态、结果等计算摘要。前端为列表生成投影，编辑公司继续使用 store 中的原始投递。历史组的状态优先使用最新状态变化，再使用结果所属状态，再按最新轮次类型推导；没有依据时显示「状态未记录」，不借用当前岗位的状态。

`PATCH /api/jobs/applications/{id}/positions/status` 保存 `{position, positionVersion, status, expectedPositionVersion, expectedStatus, expectedStatusHistoryId}`。`expectedPositionVersion` 使用原始投递的当前版本，`positionVersion` 标识目标岗位。旧状态及该岗位最后状态记录 ID 用于识别陈旧请求，无状态记录时 ID 传 `null`，历史废弃枚举可作为旧值校验。服务端锁定投递后核对目标并追加该岗位状态，过期请求返回 409，同值重试保持幂等。旧的投递状态接口继续修改当前岗位。
