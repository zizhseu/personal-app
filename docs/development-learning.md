## Q001：搜索之后返回，为什么又变成默认页面？这些机制属于前端还是后端？

记录日期：2026-10-25。

**用户原话**

> 我搜索了我投递的银行，然后选了农业银行点进去，返回后我希望看邮储银行，但是我返回发现我之前搜索的没了，又变成默认界面了
>
> 面试问答模块也有类似的问题，包括不同模块间的切换再返回也是默认。
>
> 你说的这些机制是后端还是前端机制？

**用户发现的问题与期望**

在实际浏览过程中发现上下文丢失，要求查看详情返回、跨模块切换返回时保留搜索结果及浏览位置。需要保存的视图状态包括搜索词、筛选条件、排序、页码和滚动位置；问答按分类分别记录。

**概念解释：主要属于前端**

| 机制 | 所在位置 | 能解决的问题及边界 |
| --- | --- | --- |
| URL 参数 | 前端路由及浏览器地址 | 表达搜索、筛选、排序和页码，让链接与历史记录携带明确状态；并不自动保存滚动位置 |
| Pinia | 前端内存 | 在组件卸载后保留共享状态；单独使用不能保证刷新后仍在 |
| sessionStorage | 浏览器存储 | 在同一标签页会话内保留可序列化的状态，刷新后仍可读取 |
| localStorage | 浏览器存储 | 适合需要跨会话保留的偏好；需要自行处理版本、清理和失效 |
| KeepAlive | Vue 前端组件缓存 | 在应用运行时保留组件实例，减少重建；刷新会丢失，重新激活时仍要考虑数据更新 |
| 滚动恢复 | 前端页面或滚动容器 | 离开时记录位置，列表与布局就绪后还原；需找到实际滚动容器 |

投递记录和题目内容是业务数据，由现有后端与数据库负责；本条讨论的是用户当前如何浏览这些数据。当前同一浏览器中的恢复需求不要求新增后端接口。如果以后要实现同账号跨设备恢复，再考虑将必要的偏好同步到后端。

**实现前的问题定位**

- [投递列表](../frontend/src/modules/jobs/views/ApplicationListView.vue)：`keyword`、筛选项、`page` 和排序保存在页面局部状态中。
- [问答列表](../frontend/src/modules/qa/views/QaListView.vue)与 [问答 store](../frontend/src/modules/qa/store.ts)：已有单个 `listPage` 的局部页码记忆，但搜索和筛选仍在组件中；分类变化会主动清空。尚未实现按分类隔离的完整浏览状态。
- [布局](../frontend/src/layouts/BasicLayout.vue)：当前主内容直接渲染 `router-view`，没有统一页面缓存层。

**最初讨论的方案**

建立统一前端状态层，以模块、页面和分类 ID 隔离记录；用 URL 表达可分享的查询条件，用 Pinia 与 sessionStorage 恢复页面上次状态，并单独恢复滚动位置。KeepAlive 按需使用。业务数据继续沿用既有加载与更新流程，数据增删后校正超出范围的页码，非法参数按字段规则处理。

**实现与验证进展（2026-10-25）**

用户随后授权开始开发，AI 辅助完成三类列表的统一恢复层：URL 保存显式查询条件，Pinia 与 sessionStorage 管理各列表记忆，在实际滚动区域渲染就绪后恢复位置。当前未引入 KeepAlive；列表业务数据继续沿用既有 API 与 store。新增重置入口，问答分类切换清理批量选择，手撕题保持原列表返回路径。

为解决“刚输入就进详情”的情况，进入详情前先完成列表地址更新。为避免刷新时把第 3 页错误改成第 1 页，页码校正等待数据就绪后执行。上述细节由 AI 在实现与验证中补充，不记为用户最初提出的具体实现。

## Q003：登录缓存能维持多久，如何避免每次重新扫码？

回填日期：2026-10-25。

**用户原话**

> 这个小红书的登录缓存能维持吗，能维持多久，你知道的，我不希望每次使用都需要重新登录

**概念解释与边界**

本地持久化能保留凭据，平台服务端决定会话是否继续有效。应用关闭后凭据仍在，不代表服务端永久认可。本项目没有按固定天数清除登录的机制，也不能承诺平台登录能维持具体几天。搜索引用的 30 分钟有效期是另一项机制，不能视为登录有效期。

此处登录凭据由后端在本机保存，前端负责触发检查和显示状态；与 Q001 的浏览器页面状态保持分属不同职责。

**实现与验证依据**

已实现两种采集器分别保存登录；打开连接弹窗自动检查；CLI 有效响应后保存服务端轮换的 Cookie。访客响应和临时网络异常不覆盖旧缓存。见 [登录持久化说明](content-sources.md)、[CLI 工作进程](../backend/app/modules/experiences/sources/cli_worker.py)、[登录缓存验证](validation-content-sources-2026-10-25.md)。已有登录复用经过真实页面检查，但没有持续多日的有效期实验。具体修复由 AI 辅助完成。

## Q006：GitHub 为什么有两个分支，合并后完整的 commit 记录还在吗？

记录日期：2026-10-25。

**用户原话（摘录）**

> github为啥有了俩分支？这俩分支要是合并了完整的commit记录还在吗，还是只有main的记录了

**提问背景与解释**

当时仓库包含 `main` 和开发分支 `codex/fix-baseline-bugs-and-ui`；AI 将当前开发分支推送到 GitHub，推送前没有充分说明分支位置。用户据此追问开发历史是否会在合并时丢失。

| 方式 | 合并后的历史 |
| --- | --- |
| 普通合并 / Create a merge commit | 两边原提交保留，并通过合并提交连到 main；之后删除开发分支引用，也不删除 main 已能追溯到的提交 |
| Squash and merge | main 收到一个合并后的新提交，不逐条保留原开发提交；保留的原分支仍可单独追溯 |
| Rebase and merge | 逐个重放改动，通常产生新的提交编号，历史更线性；不等同于完整保留原提交身份 |

如果目标是保留原始开发过程，普通合并符合这个目标。2026-10-25 仅解释并继续在现有开发分支提交，当时尚未执行合并。

**用户决策与实际执行（2026-10-26）**

> 那你采用普通合并吧

按用户选择，由 AI 执行 `git merge --no-ff`，将 `codex/fix-baseline-bugs-and-ui` 合并到 `main`，合并提交为 [978877a](https://github.com/zizhseu/personal-app/commit/978877ab68e4574d00bc89ad02b578fba6a3b98b)。没有压缩或重放原提交，开发分支继续保留。

- 合并前确认工作区干净，两条本地分支均与 GitHub 对应分支同步。
- 合并没有冲突，两个父提交分别是原 `main` 的 `fb4ded1` 与开发分支的 `95d28ba`。
- 核对开发分支此次新增的 8 个原提交都可从 `main` 追溯，原提交编号保持不变。
- 合并提交的文件树与开发分支完全一致；这一步通过树差异与提交可达性验证，没有把此前的测试表述为本轮重新执行。
- 本次另补本条学习记录；数据库、参考仓库和本机凭据继续排除在提交外。

## Q008：同一公司换了岗位，为什么各阶段需要保存不同岗位？

记录日期：2026-10-26。

**用户原话**

> 某个公司的岗位我投递后挂了，于是我换了一个岗位，因此在流程中，不同的阶段应该显示不同的岗位，以此让使用者完整地回顾流程。

**用户发现的问题与产品要求**

用户从实际求职过程提出：一家公司的一条记录可能先投岗位 A、失败后再投 B，历史流程不能全部显示当前岗位。要求保留各阶段当时的岗位，便于完整回顾。

**定位与技术解释**

原模型只有 `application.position`，轮次与状态历史没有岗位快照；日程使用当前岗位拼接标题，当前结果也直接取全记录的最新轮次。仅修改前端文字或缓存不能保存过去的业务事实。

本功能与 Q001 的页面记忆不同，需要后端持久化岗位快照。岗位流程使用独立代次，A → B → A 仍是三次流程；结果保存所属阶段标识，补记旧轮次时不会被放到新岗位的同名阶段。

**AI 补充的实现细节**

- 更换岗位可选择重新初筛或继续当前阶段；普通编辑更改岗位也保存历史。同名再次投递可重新开始流程。
- 当前结果、截止时间和正向状态联动限定在当前岗位流程；旧岗位结果与复盘继续保留，上一岗位的 Offer 决定不沿用。
- 历史阶段可补录岗位并同步明确关联的快照；单独更正轮次岗位时处理冲突关联，不强行归到另一岗位。旧结果无法归属时仍显示。
- 原版本已经覆盖的岗位无法从现有数据可靠恢复。迁移保留未知，提供人工补录，而不是把当前岗位补成所有历史岗位。

这些方案与边界由 AI 在实现中补充，不能表述为用户亲自设计或独立编写。

**实现、验证与参与边界**

AI 辅助修改后端模型、幂等迁移、岗位流程逻辑和前端展示；用户负责提出真实场景与回顾要求。完整后端 113 项测试、前端 20 项测试及生产构建通过；独立示例库完成改投、旧复盘、刷新、补录及窄屏验证。正式数据库先做本机备份，迁移后原记录和原字段逐项比对一致。没有声称自动还原未知历史，也没有把 AI 执行的检查写成用户亲自完成。

**AI 核对与解释**

- 当前项目已有投递、岗位历史与待办服务，业务规则可继续复用；现有文本模型调用不等同于 Agent 的工具执行循环。

**AI 提出的集成建议，尚待用户确认**

采用“当前项目 + 独立 nanobot 运行时”：当前仓库维护工作台、会话桥接、业务 MCP 工具与集成配置模板。nanobot 独立进程和环境运行，不直接导入业务 ORM，也不读写业务 SQLite；工具端在本项目服务器内复用既有业务服务。

网页经后端调用 nanobot，nanobot 经 MCP 调用业务后端，是两个方向的接口。Skill 提供工作指引，工具提供实际能力，授权与幂等由业务后端执行。机器人入口需要绑定用户；同一份业务数据与跨渠道共享聊天上下文是不同需求。

邮箱需要作为招聘资料连接器处理。本机 nanobot EmailChannel 的默认流程包括 IMAP 来信和 SMTP 回复，它不等同于只读招聘邮箱助手。应分别保存增量读取进度与 AI 分析状态，保留来源并避免重复待办；邮件发件人不能因此成为有权操作主人资料的用户。

本地独立进程支持关掉网页后继续运行，但电脑关闭后不会继续收信或响应机器人；需要常在线部署才能满足该使用方式。

建议先打通截图录入的最小业务流程，再依次验证 QQ、邮箱及微信。具体设计、源码核对边界及验收目标见 [AI 工作台架构讨论稿](agent-workbench-design.md)。这些是讨论建议，本轮仅保存文档，没有开始功能实现、授权账号或联调。

**LangChain 是否支持循环，2026-11-09**

用户原话

### 1. 如何扫描新邮件

后端启动后，会运行一个调度协程，**每 30 秒检查一次是否到期，到期后按每小时周期扫描**。手动扫描通过后台任务调用同一个 `run_scan()`，并保留原定时计划。入口分别是 `scheduler()` 和手动扫描接口。[调度代码](../backend/app/modules/mailbox/router.py)

收邮件使用 Python 标准库 `imaplib`，通过 IMAP SSL 连接 163。增量读取依赖两个标识。

- `UID` 可以理解为邮件在收件箱中的编号。
- `UIDVALIDITY` 标识这一套编号是否仍然有效。

例如首次连接时，最新邮件编号为 1000，就保存这个基线。以后检查编号大于 1000 的邮件，所以用户在其他客户端读过的新邮件也能被发现。

读取采用只读模式和 `BODY.PEEK`，保持邮件原来的已读状态。之前连接失败发生在读取游标这一步，修复后增加了 `STATUS` 查询和仅查询 UID 的兼容路径。入口为 `read_mailbox()`。[收件代码](../backend/app/modules/mailbox/imap_client.py)

### 2. AI 具体负责什么

每封需要分析的邮件，通过现有的 `llm_chat()` 发起一次请求。输入包括标题、发件人、正文、发送时间、附件文件名和已有投递的公司名称候选，要求返回结构化结果。公司候选输入是在用户后续指出全称与简称不一致后补充的实现，详见本条末尾的公司实体对齐记录。

主要包含以下内容。

- 邮件属于招聘进展、催办提醒、投递邀请、推广、无关内容还是不确定材料。
- 公司、岗位、轮次和结果。
- 开始时间、截止时间。
- 支持这些判断的原文片段。

返回后先用 Pydantic 检查格式，再检查公司、岗位、引用文字是否确实出现在邮件里。自动执行前，还会用规则核对原文中的日期和时刻，避免把截止时间误填成开始时间。提取入口为 `extract()`，时间依据检查为 `time_is_grounded()`。[AI 提取与校验](../backend/app/modules/mailbox/analysis.py)

### 3. 如何处理重复和误导邮件

这里设置了几层判断。

| 层次 | 判断方式 |
| --- | --- |
| 收件去重 | 用邮箱、UIDVALIDITY 和 UID 防止同一封邮件重复入库 |
| 内容去重 | 对规范化后的发件人、标题和正文计算摘要，识别重复发送的相同内容 |
| 事件去重 | 比较目标岗位、轮次、时间、结果及已执行事件 |
| 已有流程比对 | 核对该岗位已有的轮次安排，发现冲突时进入待核对 |

因此，“同一测评再提醒一次”会被归为提醒或重复记录。已有测评轮次，却收到时间不同的新邀请时，需要进一步判断是改期还是新增轮次。明确的投递推荐会保留忽略原因。收件及内容去重在 `store_batch()` 中处理，分类结果由 `analyze_message()` 分派，事件去重和轮次比对在 `apply_event()` 中完成。[收件与分析流程](../backend/app/modules/mailbox/service.py) · [事件执行与比对](../backend/app/modules/mailbox/execution.py)

**这些规则能减少误更新，语义分类仍可能出现误判，实际效果需要真实招聘邮件继续验证。**

### 5. 如何保证更新完整、避免并发覆盖

**邮件触发的岗位状态、轮次和更新记录，在同一笔数据库事务中提交。**

执行器通过 `commit=False` 复用原有岗位服务，等全部操作成功后统一提交。中途失败就回滚，邮件原文和提取结果保留，供重试。执行入口为 `apply_event()`。[邮件执行代码](../backend/app/modules/mailbox/execution.py) · [岗位与轮次服务](../backend/app/modules/jobs/service.py)

并发保护分成两部分。

- **扫描租约**让手动和定时任务竞争同一个执行资格，处理期间续租，过期任务的旧执行标识会失效。实现入口为 `claim_scan()` 和 `renew_lease()`。

收件游标和 AI 处理状态分别保存，所以模型超时后，可以直接重新分析已保存的邮件。主流程入口为 `run_scan()`。[任务与恢复代码](../backend/app/modules/mailbox/service.py)

前端负责配置、触发扫描、展示记录和人工核对，每 5 秒刷新处理状态。邮件及处理记录保存在 SQLite，授权码在 Windows 下使用 DPAPI 加密保存。[前端交互](../frontend/src/modules/mailbox/views/MailboxView.vue) · [邮箱数据模型](../backend/app/modules/mailbox/models.py) · [私有配置存储](../backend/app/core/private_store.py)

### 1. 每次分析会调用几次 AI

**每封进入模型分析的邮件，每次分析通过一次 `llm_chat()` 同时完成分类和字段提取。原文校验、重复判断、岗位匹配由本地代码完成。**

| 步骤 | 本步骤的大模型调用次数 | 具体实现 |
| --- | --- | --- |
| AI 分类并提取招聘事件 | 1 次，分类和提取合在同一个请求中 | 提示词与邮件材料交给 `llm_chat()`，返回 JSON 候选事件 |
| 原文校验 | 0 次 | Pydantic、字符串包含判断、日期解析和业务规则 |
| 重复判断 | 0 次新增调用 | UID、内容摘要、结构化事件键与已有轮次比对 |
| 匹配具体岗位 | 0 次 | 规范化名称后查询、过滤现有岗位分组 |

已提前判定为重复内容或明确投递推荐的邮件，可以在模型调用前结束处理。用户点击重新分析，或中断任务被接管后再次执行分析时，会产生新的一次模型请求。

### 2. 分类和字段提取如何合用一次请求

`analysis.extract()` 将固定提示词放入 system 消息，将邮件标题、发件人、正文、发送时间、附件文件名及已有公司名称候选放入 user 消息。模型在同一份 JSON 中输出类别、事件类型、公司、岗位、轮次、时间、原文引用和判断理由。`company` 保留邮件原名，`matchedCompany` 选择系统公司候选，完整岗位及代次记录由后续后端匹配步骤查询。公司候选输入及对应字段由后续公司别名反馈推动补充，调用次数仍为一次。[提取入口](../backend/app/modules/mailbox/analysis.py)

以下是虚构邮件示例。

> 示例银行邀请您参加后端开发岗位测评，开始时间为2026年11月12日10:00。

同一次模型请求可返回如下结构。

```json
{
  "category": "event",
  "eventType": "invitation",
  "company": "示例银行",
  "matchedCompany": "示例银行",
  "companyMatchType": "exact",
  "companyMatchReason": "邮件原名与已有公司候选一致",
  "position": "后端开发",
  "roundType": "assessment",
  "result": null,
  "startAt": "2026-11-12T10:00:00+08:00",
  "deadlineAt": null,
  "startEvidence": "2026年11月12日10:00",
  "deadlineEvidence": null,
  "evidence": "示例银行邀请您参加后端开发岗位测评，开始时间为2026年11月12日10:00。",
  "reason": "邮件给出了具体岗位的测评邀请和开始时间"
}
```

`category` 完成分类，`company`、`position`、`roundType` 等字段完成信息提取。后端据 `category` 分流，招聘事件进入匹配，提醒、投递推荐和无关材料保留忽略原因，不确定材料进入待核对。

### 3. 原文校验具体检查什么

首先用 `MailProposal.model_validate_json()` 检查 JSON 结构、字段类型、枚举和字段间约束。例如结果必须属于支持的枚举，截止时间不能早于开始时间，邀请和改期不能直接推断通过结果。[结果结构与约束](../backend/app/modules/mailbox/schemas.py)

随后将邮件标题和正文组成原文，检查 `company`、`position`、`evidence`、`startEvidence`、`deadlineEvidence` 的非空值是否逐字出现在原文中。这个步骤使用字符串包含判断。若模型在上面的示例中输出另一家银行名称，引用校验会失败。[原文引用校验](../backend/app/modules/mailbox/analysis.py)

自动执行前还会调用 `time_is_grounded()`，从时间依据中用规则解析日期和时刻，并与模型输出时间比较。示例原文写 10:00，模型输出 11:00 时，会进入待核对。复杂或无法确定的时间表达同样需要人工核对。`auto_review_reason()` 还检查轮次关键词和结果依据，例如“未通过”的原文不能被自动应用为“通过”。这些检查均在本地执行。[时间解析](../backend/app/modules/mailbox/analysis.py) · [自动执行依据校验](../backend/app/modules/mailbox/execution.py)

原文包含某个名称或引文只能证明这些文字有来源，邮件类别与事件语义的正确性仍依赖模型和后续规则，实际识别效果待真实样本验证。

### 4. 重复判断如何完成

去重分布在 AI 分析前后。

| 所处位置 | 使用的数据 | 处理方式 |
| --- | --- | --- |
| AI 前 | 邮箱、UIDVALIDITY、UID | 查询是否已有同一封邮件，数据库唯一约束也保护这组标识 |
| AI 前 | 发件人地址、标题和正文 | 做全半角、空白及大小写规范化后计算 SHA-256 摘要，与已保存内容摘要比对 |
| 岗位匹配后 | 投递 ID、岗位代次与名称、必要的轮次 ID、事件类型、轮次类型、结果、开始与截止时间 | 生成事件键，查询该事件是否已经成功执行 |
| 岗位匹配后 | 同岗位已有同类型轮次及其开始、截止时间 | 比对是否为同一安排，时间冲突时进入待核对 |

例如同一测评被换了标题再次发送，内容摘要可能不同，但 AI 提取出的岗位、轮次和安排时间相同，业务比对仍能识别为已有安排。模型若将邮件分类为催办提醒，后端按类别保留忽略原因。这里利用了第一步的提取结果，后续去重直接比较字段及数据库记录。[内容摘要](../backend/app/modules/mailbox/imap_client.py) · [收件去重](../backend/app/modules/mailbox/service.py) · [业务事件与轮次比对](../backend/app/modules/mailbox/execution.py)

### 5. 岗位匹配如何完成

`matching_targets()` 查询现有投递并展开各岗位分组，优先使用邮件原名的规范化精确匹配；原名没有直接命中时，接受通过候选及组织范围检查的同机构别名对应，再筛选该公司的岗位。名称规范化包括 Unicode NFKC、去除空白和统一大小写。

- 邮件需要提取出公司原名，后端按原名或通过校验的对应公司筛选。
- 邮件明确提到岗位时，再按岗位名称筛选。
- 邮件没有明确岗位时，检查该公司的候选岗位分组是否唯一。
- 唯一候选继续校验，零候选或多个候选进入待核对。
- 同名再次投递的不同岗位代次分别保留，主要岗位偏好仅用于列表展示。

### 第一轮提取事件和检索关键词

第一轮 `analysis.extract()` 只输入邮件材料，输出分类、原始公司名、岗位、轮次、时间、原文依据和 `companySearchKeywords`。例如邮储邮件可提取“邮储”“银行”“邮政”等关键词。本轮先验证 JSON 结构与原文引用，收件结果及第一轮提取结果分别保存。[第一轮提取](../backend/app/modules/mailbox/analysis.py) · [输出结构](../backend/app/modules/mailbox/schemas.py)

### 后端逐关键词搜索并合并候选

后端对每个去重后的关键词分别调用 `search_companies()`。例如三个关键词会分别查询三次，再将命中的公司名称取并集。

```text
邮储 → 中国邮储银行
银行 → 中国银行、中国邮储银行、其他银行……
邮政 → 中国邮政
              ↓
候选并集 → 中国邮储银行、中国银行、中国邮政、其他命中公司……
```

当前采用以下实现默认值，这些数量由 AI 在开发中选择，可在后续根据样本调整。

- 第一轮最多提供 5 个关键词，每个词为 1 至 40 个字符，重复关键词合并。
- 每个关键词最多返回 20 个去重公司名称，候选并集最多 100 家。
- 每个结果包含 `hasMore`，表示该关键词是否还有未返回的命中项。
- 查询使用参数绑定，并把 `%`、`_` 等通配符作为普通检索文字转义处理。

查询逻辑由邮箱服务复用，另提供 `GET /api/mailbox/companies/search` 入口。该数量限制控制交给模型的候选规模，数据库当前采用 SQLite 包含匹配，实际大规模查询延迟仍需专门测量。[关键词查询服务](../backend/app/modules/mailbox/execution.py) · [检索接口](../backend/app/modules/mailbox/router.py)

## Q011：电脑上运行的项目怎样通过局域网在手机访问？

记录日期为 2026-11-07（北京时间）。

**用户原话**

> 如何让局域网访问这个，比如现在是在电脑，我想在我的手机上也能访问

**用户需求与 AI 解释**

用户希望手机可以访问电脑上运行的项目。AI 核对现有启动脚本、Vite 配置和请求封装后，给出局域网访问的启动方式。

`127.0.0.1` 表示访问设备自身的回环地址。手机需要通过电脑的局域网 IPv4 地址连接电脑，前端服务也需要监听局域网接口。Vite 的 `--host 0.0.0.0` 用于监听本机所有 IPv4 接口，浏览器访问时填写电脑实际的局域网地址。

本项目的浏览器请求统一使用相对路径 `/api`，由电脑上的 Vite 代理转发到 `http://127.0.0.1:8000`。手机通过前端入口即可读取和编辑电脑数据库中的记录，后端沿用现有启动方式。

**给出的操作步骤**

手机和电脑接入同一路由器的网络，停止原前端进程后，在项目的 `frontend` 目录启动局域网入口。

```powershell
npm.cmd run dev -- --host 0.0.0.0 --port 5175 --strictPort
```

手机浏览器访问 `http://<电脑局域网IPv4>:5175/`。若出现 Windows 防火墙提示，可为 Node.js 允许专用网络访问。固定端口及 `--strictPort` 由 AI 补充，用于避免端口被占用后自动换号造成访问地址混淆。

AI 补充说明，现有投递接口允许直接读取和修改记录，局域网入口开放后，可连接该入口的设备也能操作这些数据。上述命令用于用户主动启动局域网访问。

**实际核对与阶段**

已检查 [启动脚本](../scripts/start.bat)、[Vite 配置](../frontend/vite.config.ts)及 [请求封装](../frontend/src/shared/api/request.ts)，并核对当前电脑的无线网络地址。本轮提供操作说明并记录原理，手机实机访问待验证。本条记录保留用户的使用需求及 AI 的方案解释，掌握程度留待用户个人复述或操作记录补充。

### 一次操作为什么需要跨表修改

假设当前岗位和主要岗位都指向同一个待更正的岗位，用户将填错的岗位名称更正。主记录 `application` 中对应的名称、该组轮次 `interview_round` 的岗位快照、状态历史 `status_history` 的岗位快照、结果历史 `round_result_history` 的岗位快照，需要按业务规则一起更新。其他岗位通过代次、名称及关联记录限定范围。

若每更新一张表就分别提交，后续写入失败时可能留下已提交的部分变更。当前 `rename_position` 将多次更新放进同一个数据库事务，完成后调用一次 `commit()`，写入阶段异常时调用 `rollback()` 并继续抛出异常。

`rollback()` 的作用范围是当前尚未提交的事务。`commit()` 成功后，后续查询或向浏览器返回响应若遇到异常，已提交的业务变更仍然存在，重复请求需要配合幂等处理。更名流程会核对成员范围后识别已经完成的相同请求。

### SQLAlchemy 中几个操作的区别

| 操作 | 作用 |
| --- | --- |
| `add()` / 修改 ORM 属性 | 将新增对象或属性变更纳入 Session 跟踪，准备后续写入 |
| `flush()` | 执行待处理 SQL，获取自增 ID 等结果，当前事务仍可回滚 |
| `execute()` | 执行 SQL，写入受当前事务控制 |
| `commit()` | 先刷新待写入变更，再提交当前事务 |
| `rollback()` | 撤销当前事务尚未提交的写入，并恢复可继续使用的事务状态 |
| `refresh()` / `expire_all()` | 分别立即重读对象，或令 ORM 缓存过期后按需重读，协调内存对象与数据库状态 |

例如 `create_application` 先通过 `flush()` 获取投递 ID，再建立初始状态历史与初筛轮次，最后统一提交。SQLAlchemy Session 默认按需建立事务，Python 的 `try` / `except` 负责异常处理，事务状态由 Session 和数据库管理。

### ACID 与业务校验

- 原子性保证事务内的修改整体提交或回滚，整组更名的失败注入用例直接验证这一点。
- 一致性关注业务约束与数据库约束得到维护，涉及目标岗位归属、名称冲突、外键和关联范围。事务之外还需要正确的业务代码与约束设计。
- 隔离性由数据库的并发控制机制提供。更名和按岗位改状态入口先执行带预期版本条件的父记录 UPDATE，再重新读取记录并校验。SQLite 在写事务期间使用数据库级写入锁协调写入者，同时只能有一个写事务推进。
- 持久性表示数据库按自身日志与同步配置保障已提交结果。具体掉电恢复能力受数据库配置和存储环境影响，本轮验证采用内存数据库。

### 版本、成员与状态历史校验

`position_version` 表达改投流程代次。请求携带 `expected_position_version`，服务端在 SQL 条件中核对预期代次，并检查影响行数。更名还比较浏览器看到的三类成员 ID 与服务端当前集合，拒绝继续处理记录范围已变化的请求。

按岗位修改状态还核对 `expected_status` 和 `expected_status_history_id`。岗位在同一代次内可能从复筛改为初筛后再回到复筛，状态文字相同而历史已经变化，最新历史 ID 可识别这个旧请求。相同目标状态的重试直接复用现有状态，避免重复追加历史。

事务处理一组写入的原子提交，并发校验处理请求依据是否仍然有效，幂等处理重复提交的业务效果。三者共同用于维护一致性。

### 实际验证与范围

本轮由 AI 读取当前实现并重新运行以下 5 项已有回归，全部通过。
