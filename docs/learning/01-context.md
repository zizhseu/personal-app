# 01 · 上下文管理（Context Management）

> 本文件收录 Agent 方向「上下文管理」相关的面试问答。
> 格式约定：`##` 二级标题为一道问题，其后到下一个 `##` 之间的内容为答案要点（支持 Markdown）。
> 在面试八股的任意分类页点击「导入」选择本文件即可批量收录。

## 什么是大模型的上下文窗口？为什么会存在上下文限制？

- 上下文窗口 = 模型单次推理能"看到"的最大 token 数，输入与输出共享。
- 限制来源：自注意力计算量随长度平方增长、KV Cache 的显存占用、训练时位置编码的长度。
- 常见量级：8K / 32K / 128K / 1M，随模型代际逐步扩大。

## Agent 长对话场景下，上下文通常会被什么占满？如何应对？

典型占用：系统提示、历史消息、工具调用结果、检索回来的文档片段。

应对策略：

1. **截断**：丢弃最早的消息，始终保留系统提示。
2. **压缩**：用小模型把历史对话总结成摘要后回填。
3. **外置记忆**：历史落库，按需检索（把记忆 RAG 化）。

## 什么是 Context Engineering？和 Prompt Engineering 的区别？

- Prompt Engineering 关注"单次提示怎么写"。
- Context Engineering 关注"每一次推理时，窗口里应该放什么"——系统提示、工具结果、记忆、检索内容的选择与组织。
- Agent 的质量瓶颈往往不在单条 Prompt，而在上下文的组装策略。

## 多轮工具调用的结果为什么会撑爆上下文？常见处理手段？

工具返回可能是大段 JSON / 网页正文 / 文件内容，一次调用就能吃掉数千 token。

常见手段：

- 对工具结果做**摘要或裁剪**后再写入历史。
- 大结果**外置存储**，历史中只保留引用，需要时再取。
- 设置单轮与总会话的 token 预算，超预算触发压缩。

## 什么是"lost in the middle"？对上下文组织有什么启示？

模型对长上下文中**开头与结尾**的信息利用最好，中间部分容易被忽略。

启示：关键指令放开头或结尾；检索内容按相关性重排，最重要的放两端；避免把关键约束埋在中间大段文本里。
